## 範圍、風險與策略

**MVP 核心路徑**：Landing page 能正常開啟 → 訪客能操作 Calendar Demo → 透過有效入口取得下載。測試優先確保這條路徑；保留既有規格要求，不自行擴充功能或驗收門檻，也不自行豁免既有要求。

頂層案例固定 **12 個**（TC-01～TC-12），不再增加；子案例只保留驗證規格與主要風險所必要的項目。自動化驗 Demo 規則、資料不變、隱私與載入行為；人工驗跨瀏覽器、實際下載與語言／版面。

- 隱私：試用內容被保存或外送（高）。後果：違反對訪客的承諾（FR-07、NFR-01）。以整合測試監看儲存與網路 API、再加人工看網路面板，因為只有兩者合起來才同時涵蓋程式路徑與瀏覽器實況；對應 TC-06、M-9。
- 磁吸與時間換算（高）。後果：主流程 AC-01.1 結果錯。以人工算例對照單元測試與一條 e2e；對應 TC-01、TC-02。
- 取消與被拒絕的操作改了資料（高）。後果：資料悄悄損壞。每個案例同時核對事件資料與 undo／redo 歷史；對應 TC-03、TC-05。
- 動態失去互動資格後狀態丟失或監聽器殘留（高）。以注入假 `matchMedia` 的整合測試驗證；對應 TC-08。
- 非互動環境仍載入試用模組（高，NFR-05）。以 e2e 看網路請求；Playwright 模擬 `pointer`／`hover` 的能力**未驗證**（SAD），失敗時以 M-4 實機補；對應 TC-07。
- 下載入口無效（高）。後果：MVP 目標 G-01 失敗。**分開驗 `href` 與實際可下載**；對應 TC-10、M-10。
- 快捷鍵攔截整頁 Ctrl+C（高，OR-26）。設計未定案，TC-12 標「設計待確認／尚不可執行」。
- 沿用行為與 Calendar 漂移（中高）。以資料驅動的一致性案例；對應 TC-11。
- 語言偵測與保留（中）；下載敘述真實性（中，NFR-03）。

**不測範圍與原因**：Calendar 引擎的全部內部細節（由 Calendar 端測，SAD 分層 A～C，網站只驗接入後行為）；過去日降低飽和度（App 行為，REUSE-13，網站不當需求斷言）；輔助技術實測（SRS NFR-07 已列為未做的已知限制）。其餘缺口見「缺口分類」。

## 環境、資料與判定方式

**執行指令與工具版本**：尚不存在。待實作票建立後記錄實際指令、版本與通過／失敗數。

**隔離**
- 試用 store 是模組層單例（SAD ADR-02）：單元／整合測試每案例以 `hydrate` 重置；e2e 每案例開**全新 browser context**，`localStorage` 與 cookie 為空，頁面重新載入。
- 不連線真正的 GitHub、流量統計或 Vercel；自動化只檢查連結的 `href`。實際 Releases 頁由 M-10 人工確認。

**固定時鐘與時區**：2026-11-09 09:00，`Asia/Taipei`（單元用假計時器、e2e 用 `page.clock`，皆為候選做法）。示範日 = 初始化時的本地今天（SDS INV-06）。

**可重建資料**
- 種子球：開發與測試使用**符合 schema 的固定占位資料**（專案擁有者 2026-11-09 同意）：`id` 為 `focus`、`rest`、`chore`；名稱與色碼由測試固定檔提供（例如名稱「專注 Focus」「休息 Rest」「雜事 Chores」、色碼 `#3B82F6`、`#22C55E`、`#F97316`，皆為占位）。**這不代表正式名稱與色碼已核准**（OR-12）；正式內容只阻塞「種子內容的驗收」與發布，不阻塞骨架與功能。測試以 `templateId` 取用，名稱長度須符合 30 個使用者看到的字元。
- 設定固定值：`startHour=10`、`endHour=15`、`pixelsPerMinute=1`、`view='day'`、`magnetEnabled=true`（SDS DATA-02）。
- 指標座標：`y = 10:00 刻度線的 y + 分鐘數 × 1`，10:00 刻度線的 y 由實際渲染的 DOM 量得。

**判定方式（獨立 oracle）**
- 預期值來自 PRD／SRS 的規格與本計畫的**人工算例**，以字面常數寫進測試。**不呼叫 `buildTrialWorkspace`、引擎函式或任何實作輸出去產生預期值。**
- 一致性案例（TC-11）：預期值同樣由規格與人工算例給出；固定 Calendar 基準 commit（`102ae1917047aee691e88cef9c497b50df745c41`）的執行結果**只作交叉比對**。兩者不一致時，**記錄差異、來源與兩邊的值，先查原因**（規格誤讀、算例錯誤、基準行為與規格不符、實作錯誤），**不修改預期值去迎合實作**。
- 每個拒絕／取消案例同時核對「錯誤或無反應」與「資料不變」：事件集合（id、標題、起訖）、`pastLength`、`futureLength`、選取、畫面訊息。
- 外部依賴（GitHub、統計）使用可控替身或不連線。

### TC-01｜建立、調整長度、命名（AC-01.1、AC-01.15）

層級：e2e；選這層的理由：驗證從拖曳到畫面的完整路徑與「沒有時間輸入欄」。前置：空日曆、三顆球、單日 10:00–15:00、磁吸與縮放為預設。

- **1a 建立**：把「專注」球放開在離 10:30 線上方 7 像素處（相對 10:00 為 23 分鐘，離 30 為 7 ≤ 8，吸附）。預期：起點 10:30，終點 12:30（長度 120，REUSE-02），標題為球名，顏色為球色，球仍在側邊。
- **1b 調整長度**：把下緣拖到離 13:00 線下方 5 像素處（185 分鐘，離 180 為 5，吸附）。預期：10:30–13:00。邊緣先由指標換成整分鐘再判斷磁吸，避開恰好 8 像素。
- **1c 命名**：雙擊，輸入「寫 PRD」，按 Enter。預期：標題為「寫 PRD」；歷史共 3 步（建立、調整、命名）；全程沒有任何時間數字輸入欄。
- **1d（設計待確認／尚不可執行）**：球列的新增／編輯球與 radial 選單是否出現，取決於 OR-20，未定案前不寫預期。
- **1e 延伸到可見範圍外**：在 14:30 建立。預期：終點 16:30 被保存，不被拒絕（REUSE-02、REUSE-11）。
- **1f UI 範圍（AC-01.15 已定的排除項；驗證「實際未渲染」）**：不以單一 `data-testid` 作為證據。排除項：日期切換（前／後／今天）、檢視切換、起訖時間設定、磁吸開關、縮放、設定入口與設定頁、右側編輯面板、工作區名稱與切換、檔案存取入口、通知列。通過依據：(1) 以角色與可見文字／可及名稱（中英兩版）查詢，數量為 0；(2) 這些元素不存在於 DOM，不是 `hidden`、`display:none`、`aria-hidden`、離螢幕或 `disabled` 的殘留；(3) 試用區內以 Tab 走訪，可聚焦元素不含這些項目。`data-testid` 查詢只可作輔助。保留：三顆球。選擇器與可及名稱清單於實作時決定。

執行方式：自動測試路徑待實作票；尚無。

### TC-03｜取消與無效提交，資料不變（AC-01.2、REUSE-05、REUSE-09）

層級：e2e 加 store；理由：要同時看畫面與歷史。

**共同前置（每個子案例各自從頭重建，子案例之間不共用任何狀態）**
1. 全新 browser context，空日曆，固定時鐘，三顆球。
2. 建立 A：「專注」球放開於 10:00 → 10:00–12:00。建立 B：「休息」球放開於 13:00 → 13:00–15:00。標題皆為球名。
3. 做一個有效變更並復原：把 B 命名為「臨時」（1 步），再復原一次。B 的標題回到球名。
4. 人工算例：建立 A、建立 B 各 1 步，命名 1 步，復原 1 步 → `pastLength` = 2，`futureLength` = 1（非零）。A、B 都存在。
5. **記錄快照 S0**：
   - **嚴格比對項**：A、B 的 id、標題、起訖、顏色；`pastLength` = 2；`futureLength` = 1。
   - **觀察項**（記錄操作前後的值，不要求相同，也不新增不變量）：選取的區塊、焦點位置、`editingEventId`、畫面上的訊息數。

**每個子案例的判定**
1. **嚴格**：事件內容（A、B 的 id、標題、起訖、顏色）、`pastLength`、`futureLength` 與 S0 完全相同；這就是「資料沒變」。
2. **嚴格（重做後的結果）**：比對之後按一次重做，B 的標題變成「臨時」，`pastLength` = 3，`futureLength` = 0，A 不變。用來證明重做堆疊確實沒被清除。（3g 的有效對照案例不做這一步。）
3. **依操作規格分別判斷**：
   - 命名輸入欄在 Enter、Escape 之後不再顯示（REUSE-09 的提交與取消語意）。
   - 沒有任何訊息（REUSE-09、REUSE-05 明定）。
4. **觀察項，只記錄、不判定**（規格沒有定義，不自行新增不變量）：選取狀態、焦點位置、`editingEventId`，以及失焦案例中輸入欄何時關閉。基準程式碼的行為（例如雙擊進入命名會選取該區塊，`appStore.ts` 的 `setEditing`）只當記錄，不當預期值。

**命名入口與提交方式**（依規格與基準查證，來源見「Calendar 基準查證記錄」）：入口有兩個，雙擊區塊、右鍵區塊後選「重新命名」；兩者都進入同一個輸入欄。Enter 提交；失焦或點別處提交；Escape 取消；被拒絕時事件不變、**沒有任何訊息**。

**測試資料（可重建，字面常數）**：`H30` = 「字」重複 30 次；`H31` = 「字」重複 31 次；`A31` = 小寫 a 重複 31 次；`FAM` = U+1F468 U+200D U+1F469 U+200D U+1F467（1 個使用者看到的字元）。名稱長度沿用規格的「使用者看到的字元」（REUSE-09）。基準的輸入欄沒有字數上限屬性，UI 路徑可以輸入 31 字，所以下列拒絕案例走一般使用者路徑。

- **3a 取消拖曳**（獨立兩個案例）：(i) 拖球到日曆外放開；(ii) 拖曳途中按 Escape。預期：判定 1、2、3。
- **3b 無效提交（雙擊＋Enter）**（獨立三個案例）：雙擊 A，輸入 (i) 空字串、(ii) 只有空白、(iii) `H31`，按 Enter。預期：判定 1、2、3；無例外。
- **3c Escape 取消命名**：雙擊 A，輸入有效名稱「X」，按 Escape。預期：判定 1、2、3。
- **3d 無效名稱的失焦提交**（獨立三個案例，輸入同 3b）：雙擊 A，輸入無效名稱，不按 Enter，直接點試用區外的非互動文字使輸入欄失焦。預期：判定 1、2、3。
  - 預期值來源：REUSE-09 與基準程式碼（輸入欄卸載時才呼叫 `updateEvent`，被拒絕時回傳 false、事件不變）。這是**已確認規格**，不是待定。
  - 測試補齊依賴（與規格待決分開）：Calendar 既有測試只涵蓋有效名稱的失焦提交與 Enter 提交的無效名稱，**沒有無效名稱的失焦提交案例**（SRS OR-25）。網站端可直接寫這個案例；Calendar 端補測屬於另一張票，不是本案例的前置條件。
  - 規格待決：無。元件卸載時提交名稱屬於 OR-24，不在本 TC。
- **3e 右鍵選單入口**：右鍵 A，選「重新命名」，輸入 `H31`，按 Enter。預期：判定 1、2、3。
- **3f 字元計算**（獨立案例）：拒絕 `A31`、`FAM` 重複 31 次（各自預期：判定 1、2、3）。有效邊界另開案例：`FAM` 重複 30 次被接受，標題為該字串，`pastLength` = 3，`futureLength` = 0。`Intl.Segmenter` 對 ZWJ 序列在各瀏覽器的結果可能不同【未】，各瀏覽器結果記在 M-2。
- **3g 有效對照**（各自獨立，不影響其他案例）：(i) 把 A 命名為 `H30` 並按 Enter。預期：A 標題為 `H30`，`pastLength` = 3，`futureLength` = 0（有效變更清除重做，AC-01.10）。(ii) 把 A 改成與目前相同的內容並按 Enter。預期：判定 1（不佔步）與判定 3。

覆蓋與缺口：AC-01.2 與 REUSE-09 的拒絕、取消、有效邊界都有對應。「卸載時提交」屬 OR-24，另列。

### TC-04｜移動既有區塊（AC-01.7、REUSE-03）

層級：e2e。前置：10:00–12:00 的區塊 A。

1. 在距 A 頂端 20 分鐘處按住（抓取偏移 20）。
2. 把指標放開在相對 10:00 為 170 分鐘處（12:50）。新起點 = 170 − 20 = 150 分鐘，離半點線 0，落在 12:30。預期：A 為 12:30–14:30，長度仍為 120 分鐘，標題不變。
3. 預期：該次移動為 1 個復原步驟。
