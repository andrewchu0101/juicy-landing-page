## 問題與證據

**誰、什麼情境**：想了解 Juicy 產品、並想在自己的 Windows 電腦上試用的人，首發對象為台灣使用者（沿用 Calendar Brief G-05）。

**目前如何處理、造成什麼影響**：目前唯一的產品 Juicy Calendar 只有 GitHub 原始碼庫與英文 README。README 的 Setup 要求 Node.js、Rust 與 Tauri 前置條件；Windows 安裝與免安裝版的段落仍標為草稿（來源：`juicy-calendar/README.md`，2026-11-09 閱讀）。一般使用者沒有看得懂的入口，也看不到產品長什麼樣。實際影響（流失多少人、多少人想找）：**待確認**，目前沒有任何訪客數據，只有擁有者的判斷。

**尚未核實的前提**（詳見下方假設）：有一群人想要這類產品（沿用 Calendar A-01）；一個專屬頁面能讓更多人願意下載；訪客看到未簽章安裝檔的警告說明後仍願意安裝。

**現況**：landing page 尚未開始。專案目錄只有骨架（協作規則、文件範本、守衛 hooks），沒有技術棧、沒有程式碼。目前 Juicy 產品只有 Juicy Calendar 一個，沒有其他產品。

## 目標與成功判準

### G-01｜訪客試用之後，能輕易找到並下載 Windows 版

- 怎麼判斷：首頁先呈現試用（G-06），下載區位於試用區下方、在同一頁內，有一個明確的「下載 Windows 版」主按鈕，連到 Juicy Calendar 的 GitHub Releases 最新版本；免安裝 .zip 與原始碼連結為次要入口。手動驗收：在一般桌機與手機寬度各走一次，從開啟首頁到抵達下載頁不超過兩次點擊（含捲動到下載區的操作）。
- 取捨（專案擁有者 2026-11-09 決定）：下載不在第一屏，是為了讓訪客先體驗再決定；代價是下載入口較不顯眼（見 R-10）。
- 目前基準與目標：未量測。代理證據：隱私友善流量統計（見 D-03）的「下載按鈕點擊次數」，以及 GitHub Releases 公開的檔案下載次數。基準尚未取得；目標值待上線後第一段觀察期再訂，不預先假設數字。

### G-02｜訪客在下載前就知道它是什麼，以及 Windows 的限制

- 怎麼判斷：頁面清楚呈現核心賣點（不用輸入時間數字，拖曳色球排時間）、離線與無帳號、平台限制（僅 Windows 10 1803 以上 64 位元；需要 WebView2）、安裝檔未簽章時 SmartScreen 會警告以及如何繼續。每一項敘述都能對到 Calendar 已確認文件中的來源；頁面不宣稱尚未驗證的功能或平台。人工逐條對照驗收。
- 目前基準與目標：未量測。目標：頁面內所有產品敘述皆有來源，零條未驗證宣稱。

### G-03｜頁面支援繁體中文與英文

- 怎麼判斷：首次進入時依瀏覽器語言決定：繁體中文或簡體中文（含各中文地區）顯示繁體中文，其他語言一律顯示英文（2026-11-09 決定，取代原「預設一律繁體中文」）；可手動切換；兩種語言的所有文字完整，沒有漏譯或殘留另一種語言。試用軟體的介面文字跟隨網頁當下的語言。手動選擇的語言在重新整理後保留（專案擁有者提案，2026-11-09 審閱無衝突後採用）；沒有手動選過時，每次依瀏覽器語言決定；試用資料不因此保留。以字串完整性檢查加人工瀏覽驗收。
- 目前基準與目標：尚無頁面；目標為上線時兩種語言皆完整。

### G-04｜流量統計不違背「不追蹤」的產品立場

- 怎麼判斷：使用的統計工具不使用跨站追蹤、不寫入識別個人的 cookie、不載入廣告；頁面上明確說明收集什麼（含語言偏好存在訪客自己的瀏覽器）；並說明桌面 App 本身仍然離線、無遙測。上線前人工檢查頁面實際載入的網路請求與 cookie，與說明一致。
- 目前基準與目標：未量測。目標：上述三項檢查全數通過。

### G-06｜訪客不用安裝，就能在網頁上試用 Calendar 的核心功能（2026-11-09 專案擁有者決定，確定要做）

- 怎麼判斷：訪客在頁面上不安裝任何東西，就能走一遍「選球 → 拖到日曆 → 調整長度 → 命名」，全程不需輸入時間數字（對應 Calendar G-01）。試用的資料不離開訪客的瀏覽器（上線前檢查網路請求，確認沒有把試用內容送到任何伺服器）。手動驗收，加上 Calendar 既有核心流程測試的對應檢查。
- 目前基準與目標：未量測。代理證據：流量統計中「開始試用」的次數（是否可記錄此事件取決於 D-03 的工具，未確認）。試用範圍是 Calendar 功能的哪一部分尚未決定（D-05）；Calendar 的 README 與 `AGENTS.md` 指出它已有瀏覽器模式（資料存 `localStorage`，不是資料夾），可能是試用的起點，但是否採用屬於設計決定，不在此定案。
- 試用範圍（已決，D-05）：只含核心排時間流程（選球、拖到日曆、調整長度、命名）與復原／重做；試用資料不上傳，且**不保存：重新整理頁面，試用內容就消失**（2026-11-09 決定，取代原「存在訪客瀏覽器」的建議），頁面明講。試用區預設三種球：專注／藍、休息／綠、雜事／橘，所有球都有文字名稱（2026-11-09 決定；具體色碼與英文名稱待定，PRD Q-04）。日曆只顯示 10:00–15:00。新區塊起始為 120 分鐘，之後仍可在 10:00–15:00 內調整，區塊不可超出此範圍，因此最晚起始時間為 13:00（2026-11-09 決定）。試用軟體的介面語言跟隨網頁當下的語言。手機等無法互動的環境不提供互動試用（NG-08），改顯示靜態預覽；非 Windows 的桌機瀏覽器可以試用。
- 與其他目標的關係（已決，D-06）：訪客進入網站先看到試用，下載放在下方；下載仍是最終要訪客做的動作（G-01）。試用畫面為瀏覽器版，行為可能與桌面版不同，頁面須明講（見 R-08）。
- 靜態預覽（已決，2026-11-09，採專案擁有者描述的方案）：無法互動的環境（至少含手機）在試用區看到一張**不能拖曳或點擊的圖片**，內容是實際試用介面的截圖：10:00–15:00 的日曆、三種球、一個已放好的 10:00–12:00 區塊。圖下文字：「將球拖進日曆，即可建立時間區塊。請使用電腦及滑鼠體驗互動試用。」（英文版文字待定）。這張圖標示為產品預覽；Windows 下載區照常顯示。哪些環境算「無法互動」的判定方式（提案：支援精細指標與懸停才啟用互動）未決，見 PRD Q-03。這張圖要等試用實際做出來才能截，也要處理中英文兩種版本（見 R-13）。

### G-05｜新增第二個產品時，不需要重做版面

- 怎麼判斷：以暫時加入一筆「假產品」資料，確認版面能正常容納兩個產品而不需修改版面程式；驗證完移除。目前只實際展示 Juicy Calendar，不放「即將推出」的佔位內容。
- 目前基準與目標：尚無頁面。因為目前沒有第二個產品，此目標屬於預留，不是現有使用者需求，若造成過度設計可降級（見 R-06）。

## 限制、假設、風險與決策

- 限制：
  - 授權（D-01，已決 2026-11-09）：軟體本體、網站與原始碼採 MIT License；商標與專案識別（Juicy 品牌、LOGO、系列名稱）保留專屬權利，不隨 MIT 授權。公開上線前，LICENSE 檔案與商標聲明須實際加入（D-10）；在此之前仍不公開上線。授權文件規劃為根目錄的 `LICENSE` 與 `TRADEMARKS.md`，網站頁尾提供連結（專案擁有者提案，2026-11-09 審閱無衝突後採用）；版權人與品牌聲明文字待專案擁有者確認。
  - 頁面只能陳述 Calendar 已驗證的事。目前：Windows 安裝檔在乾淨電腦上未驗證、桌面版在 Windows 的實際啟動驗證狀態以 Calendar 最新文件為準（來源：Calendar README 與 Brief G-03／G-04，2026-11-09 閱讀；上線前須重新核對）。
  - 呈現桌面版的截圖與錄影必須來自 Windows 實機，驗證前只做版面，不放看似真實的假畫面。呈現網頁試用的截圖（靜態預覽）必須來自實際運作的試用頁，不是設計稿或手繪的仿真畫面，並標示為產品預覽。
  - 網站託管在 Vercel，並以 GitHub 原始碼庫連動 CI/CD（2026-11-09 決定）；網域未定（D-02）。Vercel 與 GitHub 連動後，推送可能自動產生可公開存取的預覽或正式部署，公開上線仍受 D-01 限制（見 R-11）。
  - 試用版不保存資料，與 Calendar 現有瀏覽器模式（存 `localStorage`）不同，重用程式碼時需處理（D-08）。
  - 不新增套件需先經專案擁有者同意（`AGENTS.md`）；技術棧尚未選定，留到 SAD 階段。
  - 開發工具放 D 槽（`CLAUDE.md` 第 3 節）。
- 假設（若不成立，目標受影響）：
  - A-01 除了擁有者，還有一群人有相同痛點（沿用 Calendar A-01）。若不成立，landing page 的投入價值降低。確認者：專案擁有者；時機：頁面上線後觀察 G-01 的點擊與下載。
  - A-02 一個專屬頁面比只有 GitHub README，更能讓一般使用者下載。未量測，需要 G-01 的基準後才能比較。
  - A-03 台灣首發使用者偏好繁體中文（沿用 Calendar A-03）。未驗證。
  - A-07 訪客願意先試用，再決定下載（D-06 的前提）。未驗證；以 R-10 的觀察檢查。
  - A-04 訪客看到 SmartScreen 警告說明後仍願意安裝。未驗證。
  - A-05 GitHub Releases 的連結與檔名在 D-01 定案後保持穩定。未確認，由專案擁有者在發布流程中確認。
  - A-06 專案擁有者已有或可取得網域。未確認。
- 風險：
  - R-01 頁面承諾超過產品實況，例如安裝檔尚未在乾淨電腦驗證卻寫成「一鍵安裝」。降低方式：G-02 要求每項敘述有來源，上線前對照 Calendar 最新文件。
  - R-02 未簽章安裝檔的 SmartScreen 警告嚇退訪客。接受此風險，頁面說明如何繼續安裝（沿用 Calendar R-02）。
  - R-03 使用流量統計，可能被認為與產品「不追蹤」的立場不一致。降低方式：G-04，頁面明確區分「網站有隱私友善統計」與「桌面 App 本身無遙測」。
  - R-04 授權條款已決定（D-01），但 LICENSE 檔案與商標聲明尚未實際加入（D-10），可能拖延上線。降低方式：D-10 列為上線前必須完成。
  - R-05 雙語內容在更新時漏改其中一種語言。降低方式：G-03 的字串完整性檢查。
  - R-06 為 G-05 預留的擴充彈性造成過度設計。降低方式：若實作成本明顯高於效益，可降為「新增產品時再重構」。
  - R-08 網頁試用版與桌面版行為不一致，訪客試用滿意、安裝後落差，或反過來。降低方式：頁面明講試用為瀏覽器版、資料不保存（重新整理就消失）；試用範圍只含兩邊行為一致的核心流程。
  - R-09 試用版需要持續和 Calendar 的更新同步。專案擁有者已決定重用 Calendar 現有程式碼（D-07），以降低雙份維護，但跨專案引用的方式與版本同步仍須在設計階段處理（D-08）。
  - R-10 下載放在試用下方，訪客可能只試用、沒有捲到下載區，或看不到下載入口。降低方式：用 G-01 的下載點擊與 G-06 的開始試用次數並列觀察；若比例明顯偏低再重看版面（不預設數字）。
  - R-11 專案擁有者已把 Vercel 與 GitHub 連線（陳述，未驗證）。連動後推送可能自動部署，預覽網址預設可能公開，等於在 LICENSE／商標聲明（D-10）、Windows 版驗證（D-04）與內容就緒前，就公開了頁面與下載連結。降低方式：D-10 完成前，不對外公布網址、不綁定正式網域，並確認預覽部署保護的設定；我尚未查看 Vercel 的實際設定，推送前先與專案擁有者確認。
  - R-12 試用不保存資料，訪客重新整理就失去內容，可能誤以為壞掉。降低方式：試用區附近明講「重新整理就會消失」（PRD AC-01.5）。
  - R-13 靜態預覽圖與實際試用介面不同步：試用介面改版後截圖過時，或中英文版本不一致。降低方式：預覽圖在試用介面定案後才製作，每次更新試用介面時一併重截；中英文兩種版本的處理待決（PRD Q-03）。
  - R-07 GitHub Releases 的下載次數不等於頁面成效（包含直接從 GitHub 來的下載）。降低方式：兩種代理證據並列，不以單一數字下結論。
