## 問題與證據

**誰、什麼情境**：想了解 Juicy 產品、並想在自己的 Windows 電腦上試用的人，首發對象為台灣使用者（沿用 Calendar Brief G-05）。

**目前如何處理、造成什麼影響**：目前唯一的產品 Juicy Calendar 只有 GitHub 原始碼庫與英文 README。README 的 Setup 要求 Node.js、Rust 與 Tauri 前置條件；Windows 安裝與免安裝版的段落仍標為草稿（來源：`juicy-calendar/README.md`，2026-11-09 閱讀）。一般使用者沒有看得懂的入口，也看不到產品長什麼樣。實際影響（流失多少人、多少人想找）：**待確認**，目前沒有任何訪客數據，只有擁有者的判斷。

**尚未核實的前提**（詳見下方假設）：有一群人想要這類產品（沿用 Calendar A-01）；一個專屬頁面能讓更多人願意下載；訪客看到未簽章安裝檔的警告說明後仍願意安裝。

**現況**：landing page 尚未開始。專案目錄只有骨架（協作規則、文件範本、守衛 hooks），沒有技術棧、沒有程式碼。目前 Juicy 產品只有 Juicy Calendar 一個，沒有其他產品。

## 目標與成功判準

### G-01｜訪客試用之後，能輕易找到並下載 Windows 版

- 怎麼判斷：首頁先呈現試用（G-06），下載區位於試用區下方、在同一頁內，有一個明確的「下載 Windows 版」主按鈕，連到 Juicy Calendar 的 GitHub Releases 最新版本；免安裝 .zip 與原始碼連結為次要入口。手動驗收：在一般桌機與手機寬度各走一次，從開啟首頁到抵達下載頁不超過兩次點擊（含捲動到下載區的操作）。
- 取捨（專案擁有者 2026-11-09 決定）：下載不在第一屏，是為了讓訪客先體驗再決定；代價是下載入口較不顯眼（見 R-10）。
- 目前基準與目標：未量測。代理證據：隱私友善流量統計（見 D-03）的「下載按鈕點擊次數」，以及 GitHub Releases 公開的檔案下載次數。基準尚未取得；目標值待上線後第一段觀察期再訂，不預先假設數字。

### G-02｜訪客在下載前就知道它是什麼，以及 Windows 的限制

- 怎麼判斷：頁面清楚呈現核心賣點（不用輸入時間數字，拖曳色球排時間）、離線與無帳號、平台限制（僅 Windows 10 1803 以上 64 位元；需要 WebView2）、安裝檔未簽章時 SmartScreen 會警告以及如何繼續。每一項敘述都能對到 Calendar 已確認文件中的來源；頁面不宣稱尚未驗證的功能或平台。人工逐條對照驗收。
- 目前基準與目標：未量測。目標：頁面內所有產品敘述皆有來源，零條未驗證宣稱。

### G-03｜頁面支援繁體中文與英文

- 怎麼判斷：首次進入時依瀏覽器語言決定：繁體中文或簡體中文（含各中文地區）顯示繁體中文，其他語言一律顯示英文（2026-11-09 決定，取代原「預設一律繁體中文」）；可手動切換；兩種語言的介面文字完整，沒有漏譯或殘留另一種語言（使用者資料不在此範圍：區塊標題與示範球名稱不隨介面語言翻譯）。試用軟體的介面文字跟隨網頁當下的語言。手動選擇的語言在重新整理後保留（專案擁有者提案，2026-11-09 審閱無衝突後採用）；沒有手動選過時，每次依瀏覽器語言決定；試用資料不因此保留。以字串完整性檢查加人工瀏覽驗收。
- 目前基準與目標：尚無頁面；目標為上線時兩種語言皆完整。

### G-04｜流量統計不違背「不追蹤」的產品立場

- 怎麼判斷：使用的統計工具不使用跨站追蹤、不寫入識別個人的 cookie、不載入廣告；頁面上明確說明收集什麼（含語言偏好存在訪客自己的瀏覽器）；並說明桌面 App 本身仍然離線、無遙測。上線前人工檢查頁面實際載入的網路請求與 cookie，與說明一致。
- 目前基準與目標：未量測。目標：上述三項檢查全數通過。

### G-06｜訪客不用安裝，就能在網頁上試用 Calendar 的核心功能（2026-11-09 專案擁有者決定，確定要做）

- 怎麼判斷：訪客在頁面上不安裝任何東西，就能走一遍「選球 → 拖到日曆 → 調整長度 → 命名」，全程不需輸入時間數字（對應 Calendar G-01）。試用的資料不離開訪客的瀏覽器（上線前檢查網路請求，確認沒有把試用內容送到任何伺服器）。日曆操作的規則與行為沿用 Calendar，不由本專案另訂。驗收方式：共用模組在 Calendar 端的測試通過（網站固定的版本），加上網站端的整合測試與手動驗收。沿用項目逐項記錄在 SRS 的沿用登記表（固定 Calendar 完整 commit 加來源路徑），並區分「程式碼已查證」「測試存在」「測試已執行」；截至本版，本專案尚未執行過任何 Calendar 測試。
- 目前基準與目標：未量測。代理證據：流量統計中「開始試用」的次數（是否可記錄此事件取決於 D-03 的工具，未確認）。重用方式（2026-11-09 更新，取代原 D-08 的「複製必要模組」）：維持兩個 repository，Calendar 把核心、互動元件與相關測試整理成版本化共用模組，網站以確切版本依賴；基準為 Calendar v0.2.0-beta.3（完整 commit `102ae1917047aee691e88cef9c497b50df745c41`），後續版本須經升級 PR、測試與預覽確認才進入正式網站（D-08；發布管道與權限見 D-11，未核准）。
- 試用範圍（2026-11-09 更新）：試用的日曆操作一律沿用 Juicy Calendar（引用方式見 SRS 沿用登記表），不新增 App 沒有的日曆功能，不另外維護一套行為。保留：三顆球、單日日曆、命名、選取與多選（含框選）、刪除、復原／重做、右鍵選單、剪貼簿（Ctrl／Cmd+C、V）、移動與調整長度。顯示設定：單日檢視，可見範圍 10:00–15:00（Calendar 的可見範圍設定；區塊可延伸到範圍外，不新增必須完整位於窗內的限制）；示範日為每次初始化時的本地今天（過去日降低飽和度的規則維持 App 現狀，測試可注入日期）。不開放：工作區管理與檔案存取（NG-07）；日期切換、起訖時間設定、右側編輯面板暫列排除，相依性待逐一確認（SRS OR-20）。時間規則、吸附、最小長度、超界、命名、快捷鍵與操作入口一律依 App，網站不另訂（先前網站專屬的 30 分鐘吸附、最小 30 分鐘、最晚起始 13:00、超界拒絕、狀態文字區、鍵盤移動等已撤回，見變更紀錄）。試用資料不上傳，也不保存：重新整理頁面，試用內容就消失，只屬於目前分頁。三顆示範種子球：專注／藍、休息／綠、雜事／橘，名稱中英並列（具體名稱與色碼待定，PRD Q-04）；球名與區塊標題屬使用者資料，不隨介面語言翻譯，試用的介面文字則隨網頁語言。非 Windows 的桌機瀏覽器可以試用。
- 與其他目標的關係（已決，D-06）：訪客進入網站先看到試用，下載放在下方；下載仍是最終要訪客做的動作（G-01）。試用畫面為瀏覽器版，行為可能與桌面版不同，頁面須明講（見 R-08）。
- 互動資格與靜態預覽（已決，2026-11-09）：主要輸入同時符合 `pointer: fine` 與 `hover: hover` 才開放互動，其餘環境顯示靜態預覽；只看這兩項，不看裝置名稱、作業系統、螢幕寬度，也不新增瀏覽器名稱或版本判定。輸入能力動態改變時重新判定：失去資格就取消尚未完成的操作、保留目前分頁已完成的資料並切換為預覽，恢復資格時可繼續。靜態預覽是一張不能拖曳或點擊的圖片，內容是實際試用介面的截圖：單日 10:00–15:00 的日曆、三種球、一個已放好的 10:00–12:00 區塊；圖下文字：「將球拖進日曆，即可建立時間區塊。請使用電腦及滑鼠體驗互動試用。」；圖、替代文字與圖下說明有中文與英文兩版，隨網站語言切換（英文版文字待定）；標示為產品預覽；Windows 下載區照常顯示。製作順序：先定義試用 UI 範圍，再完成互動版，最後才截圖（見 R-13）。非互動環境不載入試用模組（動態載入）。

### G-05｜新增第二個產品時，不需要重做版面

- 怎麼判斷：以暫時加入一筆「假產品」資料，確認版面能正常容納兩個產品而不需修改版面程式；驗證完移除。目前只實際展示 Juicy Calendar，不放「即將推出」的佔位內容。
- 目前基準與目標：尚無頁面。因為目前沒有第二個產品，此目標屬於預留，不是現有使用者需求，若造成過度設計可降級（見 R-06）。

## 限制、假設、風險與決策

- 限制：
  - 授權（D-01，已決 2026-11-09）：軟體本體、網站與原始碼採 MIT License；商標與專案識別（Juicy 品牌、LOGO、系列名稱）保留專屬權利，不隨 MIT 授權。公開上線前，LICENSE 檔案與商標聲明須實際加入（D-10）；在此之前仍不公開上線。授權文件規劃為根目錄的 `LICENSE` 與 `TRADEMARKS.md`，網站頁尾提供連結（專案擁有者提案，2026-11-09 審閱無衝突後採用）；版權人與品牌聲明文字待專案擁有者確認。
  - 頁面只能陳述 Calendar 已驗證的事。目前：Windows 安裝檔在乾淨電腦上未驗證、桌面版在 Windows 的實際啟動驗證狀態以 Calendar 最新文件為準（來源：Calendar README 與 Brief G-03／G-04，2026-11-09 閱讀；上線前須重新核對）。
  - 呈現桌面版的截圖與錄影必須來自 Windows 實機，驗證前只做版面，不放看似真實的假畫面。呈現網頁試用的截圖（靜態預覽）必須來自實際運作的試用頁，不是設計稿或手繪的仿真畫面，並標示為產品預覽。
  - 網站託管在 Vercel，並以 GitHub 原始碼庫連動 CI/CD（2026-11-09 決定）；網域已決（D-02，2026-11-13）：使用 Vercel 的網域。Vercel 與 GitHub 連動後，推送可能自動產生可公開存取的預覽或正式部署，公開上線仍受 D-01 限制（見 R-11）。
  - 試用版不保存資料（只在記憶體，重新整理即消失），與 Calendar 桌面版寫入工作區資料夾、也與其瀏覽器開發模式（存 `localStorage`）不同。儲存由接入方式提供：桌面接檔案儲存，網站接記憶體儲存；網站不得以 `localStorage` 保存試用內容（語言偏好除外）。日曆規則一律沿用 Calendar（例如最小長度 1 分鐘、不拒絕超出可見範圍的區塊），網站不另訂。
  - 不新增套件需先經專案擁有者同意（`AGENTS.md`）。技術棧已決定為 Vite + React + TypeScript 單頁靜態站，不新增後端、API 或資料庫（2026-11-09 決定）；套件清單與版本在實作票核准；Calendar 共用模組本身是新增依賴，其發布管道與權限見 D-11，版本於實作前確認相容性，不先鎖定未驗證版本。
  - 瀏覽器支援目標：桌機 Chrome、Edge、Firefox、Safari 最新兩個穩定版；互動資格仍只依 `pointer`／`hover`，不新增瀏覽器名稱或版本判定；不在範圍內者不保證正常運作，也不宣稱已驗證（2026-11-09 決定）。
  - Calendar 重用（2026-11-09 改為方案 B，取代複製方案）：維持兩個 repository，由 Calendar 提供版本化共用模組；網站依賴確切版本，不使用 latest；升級經升級 PR、測試、預覽確認後才發布（是否自動建立升級 PR 由 SAD 提案）。基準 Calendar v0.2.0-beta.3（`102ae1917047aee691e88cef9c497b50df745c41`）。Calendar 原始碼庫目前沒有 LICENSE 檔案（且當時為私有；2026-11-11 起已公開），來源授權與發布管道待決（D-10、D-11、R-14）。共用模組的拆分屬於 Calendar 端的改動，需另案處理，本專案此階段不修改 Calendar、不發布套件、不設定憑證。
  - 部署前檢查：CI 採 GitHub Actions（型別檢查、lint、單元測試、建置）；GitHub Actions 通過不代表 Vercel 會自動等待它，部署前的阻擋機制由 SAD 說明（2026-11-09 決定）。本階段不新增 workflow。
  - 基本搜尋與分享 metadata 納入設計，不因此增加框架（2026-11-09 決定）。

  - A-03 台灣首發使用者偏好繁體中文（沿用 Calendar A-03）。未驗證。
  - A-07 訪客願意先試用，再決定下載（D-06 的前提）。未驗證；以 R-10 的觀察檢查。
