# 加入別人的專案／接手舊專案

原則：**先當訪客，再當貢獻者。** 在弄懂對方的規矩前，不改任何東西。你的 `CLAUDE.md`、格式、工具偏好都不能蓋過對方專案已有的規則。

## J1｜唯讀盤點（第一個對話，不修改檔案）
```text
只讀，不修改任何檔案、不安裝任何東西、不執行專案腳本。
1. 列出：README、CONTRIBUTING、CODEOWNERS、AGENTS.md／CLAUDE.md、CI 設定、鎖定檔、測試目錄、docs/。
2. 說明：專案做什麼、技術棧與版本要求、怎麼啟動、怎麼跑測試、分支與 commit 慣例、PR 流程。
3. 用 git 唯讀指令報告：目前分支、HEAD、最近 20 筆 commit 的風格、工作樹是否乾淨、最近誰在改哪些區域。
找不到的資訊標「找不到」，不要猜。
```

## J2｜建立基準線（跑之前先確認會寫什麼）
```text
依 README 建立隔離環境（虛擬環境放專案內，不裝全域套件），跑一次完整測試，保留完整輸出。
回報：通過／失敗／略過數量、環境版本、耗時。**原本就失敗的測試逐一列出並記錄**，不要修，也不要刪。這是我的基準線，之後才能分辨「我弄壞的」與「本來就壞的」。
```

## J3｜找到我該做的那一小塊
```text
我被指派的工作是：＜issue／需求＞。
找出相關的程式、測試、文件。列出你打算改動的檔案與理由、可能的影響範圍，以及需要先問專案負責人的問題。先不改，等我確認。
```

## J4｜小步修改
```text
只做這個 issue 需要的最小改動，沿用既有風格與命名。不順手重構、改名、升級依賴或格式化無關檔案。
先寫會失敗的測試（若專案有測試慣例），再改程式。完成後跑完整測試，與基準線比較：新增失敗為 0。
```

## J5｜提交前檢查（人看）
```text
列出 git status 與 git diff 的摘要：每個變更檔案為什麼改。逐檔明確 stage（不用 git add . 或 -A）。
檢查：沒有無關檔案、沒有秘密、沒有大型生成檔；commit 訊息符合專案慣例。不要 push，等我確認。
```

## 先問再做的事
- 想改的範圍超出 issue。
- 要升級依賴、改建置或 CI。
- 發現疑似 bug 或安全問題 —— 先回報負責人，不要自己默默修，也不要在公開地方貼出細節。
- 專案規則與你自己的偏好衝突 —— 聽專案的。
