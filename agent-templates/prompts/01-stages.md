# 正式專案階段卡（A–K）

文件路徑以你專案實際為準；以下沿用 `docs-templates/` 的編號（`docs/01-brief.md` … `docs/06-test-plan.md`）。
每張卡的最後都有「人的審查」—— 沒過就不進下一張。

---

## A｜需求訪談與 Brief　`/grill-with-docs`
```text
/grill-with-docs
先讀 @AGENTS.md（或 @CLAUDE.md）與 @README.md。
依 @docs-templates/01-brief.md 整理 Brief：問題、來源、可觀察目標、非目標、限制與風險；尚未核實的前提與未量測的指標要明記。
已固定的技術與功能不重問；訪談只聚焦會影響產品方向的未決問題，最多兩輪。每題給建議，等我回答，不自行定案。
共識確認後寫 docs/01-brief.md，依模板 Gate 回報缺口。未決且影響核心流程的，列出決策人與期限，不開始寫程式。
```
**人的審查**：問題有來源或標示為待確認；目標可驗；影響範圍的決策已定案或有負責人。

## B｜寫成最小 PRD　`/to-spec`
```text
/to-spec
依 @docs/01-brief.md 與剛才確認的決策，使用 @docs-templates/02-prd.md 產出 docs/02-prd.md。
只處理 PRD：2–3 個使用者故事、AC 不超過 10 條，至少涵蓋成功、拒絕輸入（不產生副作用）、查看結果。標示使用者情境、成功與失敗回饋、持久結果。
不加入範圍外的功能；不建立尚未進行的 SRS 與設計文件。不要替我補未決問題；完成後依 Gate 列出需人工審查的 AC 與產品決策。
```
**人的審查**：有成功與失敗條件；每條 AC 可判斷；沒有新增範圍。

## C｜從 AC 到系統規則　`/to-spec`
```text
/to-spec
讀 @docs/02-prd.md，依 @docs-templates/03-srs.md 產出 docs/03-srs.md。
每條 FR 引用 AC；FR 不超過 10 條。用規則字典與邊界例子確認：必填、合法值、反向或空範圍、狀態由誰決定、資料隔離。品質要求要可觀察；效能門檻須有依據，否則記「待量測」。
出現矛盾就列出，不擅自選邊。不重建 PRD、不寫程式。依 Gate 列出沒被 SRS 承接的 AC，以及仍無法獨立算出預期結果的規則。
```
**人的審查**：每個 AC 在 SRS 有對應；規則能獨立算出預期值。

## D｜用圖檢查流程　`/archify`（沒有就用 Mermaid）
```text
/archify
讀 @docs/03-srs.md，把主要使用者流程畫成 workflow，輸出 diagrams/＜名稱＞.html，保留來源檔與工具實際驗證結果。
包含：起點、輸入、後端驗證、錯誤回饋且不產生副作用、成功路徑、使用者看到的結果。只畫 SRS 已定的行為，不自行加功能。
完成後回報實際檔案路徑與檢查結果。工具或環境不足就明說原因，改在 docs/03-srs.md 用 Mermaid 寫，不假裝已產出 HTML。我會對照 SRS 逐一審圖，未確認前不修改需求。
```
**人的審查**：圖與 SRS 一致；成功、拒絕、不產生副作用的分支都有。

## E｜SAD 與 SDS　`/to-architecture`
```text
/to-architecture
讀 @docs/02-prd.md、@docs/03-srs.md、＜技術棧文件＞ 與剛確認的流程。依 @docs-templates/04-sad.md、@docs-templates/05-sds.md 產出 docs/04-sad.md、docs/05-sds.md。
定清：元件責任、信任邊界、資料欄位、介面（請求／回應範例、錯誤格式）、不變量、故障回饋，以及測試時如何注入暫存資料庫與固定時鐘。
有真正取捨才寫 ADR，不為湊篇幅。部署不在範圍時，記「不適用」的原因與上線前缺口。核心決策未定先問，不寫程式。依 Gate 回報沒有設計落點的 FR/NFR。
```
**人的審查**：責任與信任邊界明確；介面與欄位可讓兩個人獨立實作。

## F｜測試計畫與預期結果　`/to-test-plan`
```text
/to-test-plan
讀 @docs/02-prd.md 至 @docs/05-sds.md，依 @docs-templates/06-test-plan.md 建立 docs/06-test-plan.md。
先列高風險與關鍵路徑，再提出 6–12 個代表性 TC 供我審預期結果。預期值來自規格與人工算例，**不呼叫實作程式去算答案**；拒絕案例要核對「資料沒變」。
另列人工操作流程。沒有執行證據的一律標「未執行」。寫明隔離資料、可重建資料、執行環境、退出條件。若風險超出案例預算，指出缺口讓我決定範圍。我確認後才寫入。
```
**人的審查**：每個 TC 有來源與人確認過的預期值；高風險有案例。

## G｜拆工作票　`/to-tickets`
```text
/to-tickets
依 @docs/05-sds.md、@docs/06-test-plan.md 拆票。第一張是骨架（建專案設定、最小入口、health 檢查與一個測試，不寫業務邏輯）；其餘按「可觀察成果」切成縱向切片。
每張票寫：成果、對應 TC、驗收指令、要讀的規格段落、真正的阻塞依賴。列出估計大小；範圍過大先報告。
先給我審清單，再寫檔。同時建立 docs/LESSONS.md（依模板），並在 AGENTS.md 的「本專案」段補已確認的規則。
```
**人的審查**：票可在新對話獨立接手；依賴是真的，不是「看起來該先做」。

## H｜一票一對話，逐行為實作　`/implement`、`/tdd`
第一段（骨架票）：
```text
/implement
完成 @issues/000-skeleton.md，遵守 @AGENTS.md 與技術棧文件。使用專案虛擬環境，讓入口可啟動、跑 health 測試、實際啟動並回報網址。不寫業務邏輯，完成後停止，等我驗收。
```
骨架驗收後，**另開新對話**：
```text
/implement
讀 @issues/001-＜名稱＞.md 與它引用的規格。依 /tdd 一次一個行為：第一個業務測試先跑出「預期原因」的紅燈，停下讓我確認，再做綠燈。其後按同樣循環完成。
每個測試標 TC 與需求編號；資料庫用暫存位置；不能改測試去放寬條件。完成後跑完整測試、操作核心流程、回填追溯表與實際偏差。
用虛擬環境的明確路徑執行，不假設 shell 已啟用 venv。不要自動 commit 或 push，未驗證項明確列出。
```
**人的審查**：親眼看到紅燈的原因；測試真的執行過；拒絕輸入不產生副作用。

## I｜有證據的除錯　`/diagnosing-bugs`
```text
/diagnosing-bugs
先讀 @AGENTS.md 與 @docs/06-test-plan.md。失敗指令、完整輸出與重現步驟如下：
＜貼真實錯誤＞
先分清是環境、規格矛盾還是實作錯誤。建立能穩定重現的檢查，一次只驗一個原因。修實作前讓我看到失敗證據；修復後跑相關與完整測試。不得放寬測試以求通過。
記錄原因、修改與實際結果；不能重現或未驗證就如實標明。
```
**人的審查**：有修復前後的證據；舊測試仍通過。

## J｜需求變更先分析影響　`/grill-with-docs`
```text
/grill-with-docs
變更需求：＜一句話＞。
讀 @docs/02-prd.md 至 @docs/06-test-plan.md，先列出受影響的 AC、FR、介面驗證、畫面、TC 與程式位置。這一步先不改程式，讓我確認。
確認後依序更新：規格 → 案例 → 測試 → 程式，並建立變更票。實作另開新對話用 /implement：先新增「新規則會拒絕」的測試，看它在舊實作失敗，再改程式。原本有效的測試仍須通過；若某測試的期待因規格變更而需修訂，先列明依據由人確認。
```
**人的審查**：影響範圍完整；順序是規格 → 案例 → 測試 → 程式。

## K｜交付檢查與展示　`/code-review`
```text
/code-review
審查範圍：＜基準 SHA／分支，或「目前已暫存與未暫存的改動」＞。
對照 @AGENTS.md、已確認規格、工單與 @docs/06-test-plan.md，分別檢查「規範」與「需求」。
執行完整測試；實際走一次成功、拒絕（不產生副作用）、重新整理後資料仍在的流程；沒有瀏覽器工具就列出給我人工操作，不宣稱已驗證。
抽查一條 AC → FR → 介面 → TC → 測試斷言與結果；確認沒有金鑰、資料庫或虛擬環境被加入版控。
在 docs/DELIVERY.md 記錄：啟動指令、實際環境版本、測試與人工驗收證據、未完成項。修正阻擋交付的問題後再驗證。先給審查結果，不自行 commit 或 push。
```
**人的審查**：他人能依 README 啟動；測試與人工操作有證據；沒有秘密。

## 換人／換對話　`/handoff`
```text
/handoff
把目前進度寫進 docs/HANDOFF.md 最上方摘要（依 @docs-templates/09-HANDOFF.md）：目標、分支與 HEAD、已完成、進行中、阻塞、下一步（最多三項）、測試與人工驗收與 commit／push 狀態。
只寫查得到的事實並附證據。寫完後，把你認為接手者最可能誤解的一點列出來。
```
